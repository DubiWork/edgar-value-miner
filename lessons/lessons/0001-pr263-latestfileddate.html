PR #263 — latestFiledDate

data-layer feat issue #250

Why does this utility exist?

The cacheWriter Cloud Function stores SEC data locally so we don't hammer the EDGAR API every time. But how does it know if the cached data is stale — i.e., if Apple filed something new since we last fetched?

The answer: compare the most recent filed date in the cached blob against the one in the freshly-fetched blob. If they differ, re-normalize. If not, skip.

latestFiledDate does exactly one thing: scan a raw SEC companyfacts JSON blob and return the latest filed date string it finds. That's it.

What does the SEC blob look like?

{
  facts: {
    "us-gaap": {
      "Revenues": {
        units: {
          "USD": [
            { filed: "2024-11-01", val: 391035000000, ... },
            { filed: "2023-10-27", val: 383285000000, ... }
          ],
          "shares": [ ... ],
          "USD/shares": [ ... ]
        }
      },
      "NetIncomeLoss": { ... },
      ...
    },
    "ifrs-full": { ... }   // only for foreign filers like SAP
  }
}

Every filing event gets a filed date. The most recent one across all tags and all unit types tells us when Apple last filed anything.

The implementation — 13 lines

export function latestFiledDate(companyFactsJson) {
  const usGaap = companyFactsJson?.facts?.['us-gaap'];
  if (!usGaap) return null;          // IFRS filers, empty blobs, nulls

  let max = null;
  for (const tag of Object.values(usGaap)) {
    for (const entries of Object.values(tag.units ?? {})) {
      for (const { filed } of entries) {
        if (filed && (max === null || filed > max)) max = filed;
      }
    }
  }
  return max;
}

Key design choices:

  • us-gaap only — IFRS filers (SAP, ASML) have no us-gaap key. The guard if (!usGaap) return null handles them. This is intentional — IFRS support is deferred to #252.
  • String comparison — ISO dates (YYYY-MM-DD) sort correctly as strings. "2025-06-15" > "2024-03-01" is true. No Date parsing needed.
  • Returns null, not undefined — consistent with the gaapNormalizer.js null convention.

The 6 Acceptance Criteria — and what we learned from each

AC1: Function exported from src/utils/latestFiledDate.js
Simple location contract. Tells the agent exactly where to put it.
AC2: Accepts raw SEC companyfacts JSON, returns max filed string (ISO format)
Specifies the input shape AND output format. "ISO format" prevents returning a Date object.
AC3: Returns null (not undefined) when facts is missing or empty
"Not undefined" is load-bearing — callers do === null checks. A missing word here would have caused a subtle bug.
AC4: Handles multiple unit types (USD, shares, pure) — scans all unit arrays
This is why the loop goes 3 levels deep. Without this AC, an agent might only scan USD and miss a later filing in a shares entry.
AC5: Unit tests using existing AAPL fixture data
⚠️ This AC caused two review iterations. "Existing AAPL fixture" was ambiguous — no raw SEC fixture existed in the repo. We resolved it by slicing real EDGAR data into src/__fixtures__/aaplCompanyFacts.js. Lesson: when an AC references "existing" data, verify it exists before writing the AC.
AC6: Non-breaking — no changes to existing normalizer behavior
Scope guard. Prevents an agent from "helpfully" touching gaapNormalizer.js.

What the review rounds taught us

  1. Round 1 — Tests used inline synthetic data, not the AC5 fixture. Also: the multi-unit test body was truncated in the diff — AC4 was unverifiable.
  2. Round 2 — Tests used real fixture, but tests 1 and 2 were identical (same input, same assertion). No isolation.
  3. Round 3 — Duplicate test fixed. AC4 IFRS scope test added. All 7 tests pass. Clean.

What this means for #251 and #252

Three patterns to carry forward:

  • Name the fixture in the AC. Don't say "using existing fixture data" — say "using src/__fixtures__/aaplCompanyFacts.js".
  • Each test must isolate one thing. If two tests share the same input and assertion, one is dead weight. For #251 (tag stitching), write one test per era — not one test that "covers eras" with the same blob.
  • IFRS is a known boundary. Any utility that reads us-gaap must explicitly test what happens with an IFRS-only blob. We established this pattern here — carry it into #251 and #252.
